操作系统概述

什么是操作系统？

​操作系统（Operating System，OS）是指控制和管理整个计算机系统的硬件和软件资源，并合理地组织调度计算机的工作和资源的分配；以提供给用户和其他软件方便的接口和环境；它是计算机系统中最基本的系统软件。

当然是操作系统		 固件也是操作系统 gdb（linux环境下的一个调试工具）也是操作系统

都是操作系统		 Hadoop也是操作系统 资源管理器也是操作系统

总之就是最高主管一般的存在，按照这样的定义，很多事情都有ta的主管，故操作系统不严格来说只是一个使得系统功能使用起来更方便的一层虚拟化

实验：实现 pstree 打印进程之间的树状的父子关系

了解pstree命令

pstree是Ubuntu默认安装的程序，用于读取 Linux 内核里保存的全部进程信息，然后以树形排版打印在终端。

参数 作用
-p 显示 PID，最常用
-u 显示进程所属用户名
-a 显示进程完整启动命令
-h 高亮你当前所在的这条进程链
-n 按 PID 数字从小到大排序（默认按名字）
-c 强制展开，不合并多个同名子进程
实验要求

复刻pstree，写一个能把系统中的进程按照父亲-孩子的树状结构打印到终端的程序，同时需要保证这三个可选项。

  • -p, --show-pids: 打印每个进程的进程号。
  • -n --numeric-sort: 按照pid的数值从小到大顺序输出一个进程的直接孩子。
  • -V --version: 打印版本信息。

多处理器编程

现代多处理器编程难到爆炸！属于比较热门的研究方向。为什么难？

  1. 内存可见性：每个CPU都有几级缓存，修改的内容不一定立刻写回主存
  2. 竞态条件：一条高级语言语句会被翻译成多条机器指令，两个cpu并行执行就会发生数据竞争，但又不是每次都会竞争
  3. 锁带来的问题：死锁、活锁、优先级翻转、粒度权衡、锁竞争
  4. 编译器+cpu双重重排序：编译器优化会调整指令顺序，而cpu硬件会调换访存顺序 为了最大化吞吐
  5. ……..

所以，我们接下来下处理多处理器编程，做了非常大的==简化==，我们的默认假设是：
指令是原子的（一条机器指令要么做完 要么没做 不会有中间状态）
内存是全局一致的
这是在硬件上解决的问题，我们暂时假设硬件已经帮我们搞定了，先不去研究how。我们只专注研究：指令交错执行带来的同步与临界区问题。

并发问题

并发 是指系统能够同时处理多个任务 但不要求任务在同一时刻真正执行。
想要做到并发，首先要解决下面的问题

问题1：两个任务同时需要访问一个资源（互斥）
临界资源：多个进程不能同时访问的资源
临界区：访问临界资源的那一段代码
问题2：进程间的执行顺序混乱（同步）
例如生产者消费者模型如何保证不崩溃

软件方法的问题是 “没有原子操作”（比如flag和turn的修改可能被打断），而 CPU 提供了原子指令（指令执行过程中不能被打断），可以直接实现互斥。

信号量

较为核心的同步互斥机制，能够解决同步与互斥，还能避免忙等

定义

信号量是一个包含“资源计数”和“阻塞队列”的结构体

配套两个原子操作：P（wait）、V（signal）。（PV操作是原子的，是操作系统靠硬件原子指令保证的）

**P(S)**：

  1. S.value--（申请一个资源，计数器减 1）；
  2. 如果S.value < 0：当前进程阻塞，加入S.list队列，释放 CPU（满足 “让权等待”）。

**V(S)**：

  1. S.value++（释放一个资源，计数器加 1）；
  2. 如果S.value <= 0：从S.list队列唤醒一个阻塞进程，让它继续执行。
优势

支持阻塞等待，资源不足时进程休眠，不浪费CPU
有计数能力，不仅能解决互斥，还能解决同步。

局限

P/V操作分散，靠手写，难以排查问题

实现轻量级的用户态协程（coroutine，“协同程序”），可以在一个不支持线程的操作系统上实现共享内存多任务并发。
实现协程库co.h中定义的API：

  1. co_start(name, func, arg) 创建一个新的协程，并返回一个指向 struct co 的指针 (类似于 pthread_create)。
    • 新创建的协程从函数 func 开始执行，并传入参数 arg。==新创建的协程不会立即执行==，而是调用 co_start 的协程继续执行。
    • 使用协程的应用程序不需要知道 struct co 的具体定义，因此请把这个定义留在 co.c 中；框架代码中并没有限定 struct co 结构体的设计，所以你可以自由发挥。
    • co_start 返回的 struct co 指针需要分配内存。我们推荐使用 malloc() 分配。
  2. co_wait(co) 表示当前协程需要等待，直到 co 协程的执行完成才能继续执行 (类似于 pthread_join)。
    • 在被等待的协程结束后、 co_wait() 返回前，co_start 分配的 struct co 需要被释放。如果你使用 malloc()，使用 free() 释放即可。
    • 因此，每个协程只能被 co_wait 一次 (使用协程库的程序应当保证除了初始协程外，其他协程都必须被 co_wait 恰好一次，否则会造成内存泄漏)。
  3. co_yield() 实现协程的切换。协程运行后一直在 CPU 上执行，直到 func 函数返回或调用 co_yield 使当前运行的协程暂时放弃执行。co_yield 时若系统中有多个可运行的协程时 (包括当前协程)，你应当随机选择下一个系统中可运行的协程。
  4. main 函数的执行也是一个协程，因此可以在 main 中调用 co_yield 或 co_wait。main 函数返回后，无论有多少协程，进程都将直接终止。
什么是协程

有点像简单版的进程，和进程的行为有相似的地方，但没那么难。协程是执行到一半时可以暂停或恢复执行的函数。
普通的函数返回后栈帧就会销毁，但协程需要保留 后面再从暂停的地方继续 再返回

除了return的新方法

实现切换协程但不使用return的方法是：**setjmp/longjmp**

这是一个可以实现跳转的指令
setjmp用于保存当前的程序执行状态，以便在稍后的某个时刻通过longjmp跳转回来

挑选的下一个协程 一定会保存好状态吗

显然是不会的，对于一个协程 我们将状态存入jmp_buf 当且仅当该协程调用setjmp时，若自己从未主动jmp过（如果启动过的话 那么一定主动jmp过，所以当前是仅创建但未启动的新协程）但又被随机选中了的话，就需要stack_switch_call 而不能直接longjmp（longjmp的参数是状态 而状态仅在setjmp时保存）。
stack_switch_call 可以切换堆栈后并执行函数调用 且能传递一个参数

这个entry函数其实应该是协程的func函数在它的栈上从头开始运行，但我们不能直接传该函数，因为我们是jmp而不是call过去的（栈里不压返回地址），函数运行完找不到返回地址 会读到错误的地址并崩溃，我们包装一个entry函数，调用完协程的func函数后改变协程的状态并yield走 更方便。

void *arg 其实就是 struct co *arg ，stack_switch_call 是通用发射器，所以需要这样写。

协程所需要的（数据结构）

全局变量：所有协程列表头指针，当前运行的协程，main的协程
一个协程的变量：名字，入口函数，入口参数；协程状态（刚创建、运行过/时、等待协程、已结束），寄存器现场（jmp_buf），私有栈，下一个协程的指针

其中，uint8_t 是无符号一字节类型（unsigned char），这是一块内存，用于协程的独立栈空间。 __attribute__()是GCC特性，aligned(16) 要求这个数组的起始地址必须是16的倍数
为什么要这样？Linux64位调用约定（x86-64 System V ABI）强制要求：函数调用时，栈指针rsp必须保持16字节对齐，否则部分指令的函数会崩溃，报段错误
